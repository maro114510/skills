# pr-doc-review-pe

設計ドキュメント PR を 3 軸でレビューし、致命的になりうるものだけを指摘する orchestrator。3 軸は形式・論理矛盾/技術前提/データモデリング矛盾・書いてない不文律/気づいていない致命的欠陥である。軸1と軸2は書いてある内容を検査する Pass 1 が、軸3は書いていないことを検査する Pass 2 が独立に担当し、後で統合する。

## レビューの原則

1. **接地された致命度ファースト** — すべての指摘を次の形式に接地する。
   「この設計は [X] を前提とする。[X] が偽なら [具体的障害 Y] が発生する。」
   そのうえで致命度ゲートを通す: 本番障害・データ不整合・移行失敗・ロールバック不能・API/データ契約の破壊に直結するものだけ出力する。抽象的な「[X] を検討しては?」は禁止。落とした候補は FN log に残す。
2. **textlint 的指摘の全廃** — typo・表記揺れ・段落体裁・行番号誤り・命名の好み・曖昧語の孤発検出は一切しない。これらは指摘対象外。形式を扱う軸1の判定対象は ADR/Design Doc の必須要素充足と論証の連続性のみであり、typo・表記揺れ・体裁とは明確に区別する。
3. **代替は設計レベルで問う** — API 名・テーブル名・カラム名レベルの代替は提示しない。主軸は「そもそもこれをやるべきか」「根本的に優れたアプローチはないか」。より良い設計が見えたら名指しで提示し、scalability・ops-complexity・reversibility・debuggability の 4 軸で比較したうえで、採否は `[ask]` で著者に委ねる。
4. **簡潔第一** — 観点カバレッジ表の各セル・指摘の「現状」「あるべき姿」は目安 1〜2 文に収める。長さの上限は厳格な足切りではなく目安とし、致命的な指摘が圧縮されて意味不明になることを避ける。詳細な論証は「指摘」セクションに書き、表は要約に徹する。
5. **軸2/軸3の切り分け** — ある候補が軸2・軸3どちらの「[X] を前提とする」形式にも当てはまりうる場合は、判定に使った事実の種類で機械的に決める。
   - 文書内の別記述・外部の一次情報・既存コードと矛盾する、または前提として明示されているが未検証なら軸2とする。
   - その観点について文書のどこにも記述が無いなら軸3とする。
   - 両方の性質を持つ、または迷う場合は軸3を優先する。
   - 軸判定は個別の主張・欠落点を指す claim 単位で行い、同一箇所から複数の異なる軸の指摘が派生してよい。無理に1つへ統合しない。
   - 軸1の論証の飛躍と軸3のより良い設計の選択肢が同じ箇所から生じる場合は軸3を優先し、軸1側は独立指摘にしない。
   - 軸2の判定に使う事実が Step 2 の接地調査で確認できていない場合は軸3として扱い、severity は `[ask]` を上限とする。

## Step 1: PR 特定とデータ収集

```bash
pr-review-pe-identify-pr.sh "$ARGUMENTS"
```

PR を特定できない場合の exit code 2、gh 障害時の exit code 3 では処理を止めてユーザーに案内する。
返却 JSON の `number` を `$PR_NUMBER`、`baseRefName` を `$BASE`、`headRefName` を `$HEAD`、`body` を `$PR_BODY` として使う。`comments`・`reviews` も同じ JSON に含まれているので、別途 `gh pr view` を呼び直さずそのまま既存コメントとして使う。

並列で取得する:

```bash
gh pr diff $PR_NUMBER                              # diff (ハルシネーション防止の基盤)
git log --oneline -n 20 origin/$BASE..$HEAD         # コミット履歴
```

diff から、変更した .md ファイルの一覧、ADR・RFC・Design Doc・実装計画のいずれかというドキュメント種別の推定、名詞・ドメイン概念語 5〜10 件のキーノウンを記録する。

## Step 2: 接地調査

キーノウンをコードベースと照合し、軸2の技術的前提を裏取りする。軸3の repo 証拠接地・ライブラリ制約確認の基盤にもなる。

```bash
git grep -n "<キーノウン>" -- '*.go' '*.ts' '*.py' '*.java' '*.kt' '*.rb' '*.sql'
```

データモデリング矛盾の検査に備え、`schema.sql` や `migrations/` 配下のスキーマ定義ファイルも対象に含め、ドキュメントが前提とするテーブル・カラム・NOT NULL や UNIQUE などの制約が実在するかを確認する。ヒットしない語はユビキタス言語ドリフトの候補とし、ヒットした語は定義とドキュメントの記述を照合する。
この手順は必ず実行し、ゼロヒット語のリストと一致したコード行をトランスクリプトに残し、Pass 1 と Pass 2 の起動プロンプトに含める。

## Step 3: Pass 1 — 軸1: 形式、軸2: 論理矛盾・技術前提・データモデリング矛盾

`Agent` を subagent_type: general-purpose で 1 つ起動し、Step 1・Step 2 のデータとして diff・既存コメント・git grep 結果を渡す。文書を精読し、書いてある内容そのものに潜む欠陥を探す。低 confidence でも候補を保持し `doc-path:line` + 引用元を返す。

### 軸1: 形式 — 構造的完全性・論証の連続性

typo・表記揺れ・体裁は原則2の通り対象外とし、判定対象は次の2点のみとする。

- **必須要素の欠落**: ADR なら Nygard 5 構成要素・Olaf Zimmermann 7 質問・Consequences-negative、Design Doc なら目的・スコープ外・代替案、RFC なら motivation・proposal・検討した代替案・unresolved questions、実装計画書なら作業スコープ・作業手順・完了条件・依存関係の要素が揃っているか。参照: `skills/pr-doc-review-pe/references/adr-checklist.md`, `skills/pr-doc-review-pe/references/design-doc-checklist.md`。
- **論証の飛躍**: 「〜を選択した」「〜は対象外とした」「〜を採用する」といった意思決定文を全件抽出し、前後 3 段落以内に明示的な根拠があるか確認する。なければ MISSING_RATIONALE として著者への probing question を生成する。

### 軸2: 論理矛盾・技術前提・データモデリング矛盾

- **文書内論理矛盾**: 「X が Y を担う」「状態は A が保持する」といった責務割り当て文を全件抽出し、二者が同一責務を主張する、または誰も担わない穴を指す Process 矛盾、「常に X」と「Y の場合は X しない」のような Policy Reversal、順序やタイミングの食い違いである Temporal 矛盾、一般クレームと特定クレームが両立しない Specificity 矛盾を検出する。発見ごとに Claim A 引用 / Claim B 引用 / 矛盾種別 / 両立不能な理由を 1 文で出す。
- **暗黙の技術的前提**: 各仮定を必ず「この設計は [X] を前提とする。[X] が偽なら [具体的障害 Y] が発生する。この前提は文書に明記されていない。」形式で出す。X が要件・制約として明記されておらず、かつ Y が本番障害・データ不整合・CS 問い合わせ増加に直結する場合にのみ出力する。参照: `skills/pr-doc-review-pe/references/premortem-and-5whys.md`。
- **技術的前提の事実誤り**: ドキュメントが明示的に主張する API/mutation 名・ライブラリの挙動・制約といった技術的事実が一次情報と食い違っていないか。不確かな場合は `WebFetch` で一次情報を確認する。「書いてあることが単に間違っている」ケースであり、軸3 の「書いていない制約」とは区別する。
- **データモデリング矛盾欠陥**: ドキュメントが前提とする NOT NULL・UNIQUE・外部キーなどのテーブル・カラム・制約が Step 2 で確認したスキーマと一致するか。既存カラムの書き込み元・一意性制約・インデックスの意味が新設計と両立するかを検証する。
- **ユビキタス言語ドリフト**: ゼロヒット語の用語ドリフト、ドキュメントの用語が実装のエンティティ・カラム・型と対応しないケース。参照: `skills/pr-doc-review-pe/references/ubiquitous-language.md`。

## Step 4: Pass 2 — 軸3: 書いてない不文律・気づいていない致命的欠陥

Pass 1 とは独立に `Agent` を subagent_type: general-purpose で起動し、Step 1・Step 2 のデータのみを渡す。Pass 1 の発見は渡さない。「書いてある内容」に引きずられず、「あるべきなのに無いもの」を白紙から想像させるためであり、これが本スキルの主眼である。

各観点で「あるべきなのに文書に無いもの」を探し、見つけたら具体的障害シナリオに接地して出す。

- **不文律・暗黙の組織的前提**: 既存 ADR・CLAUDE.md・実装パターン・他チームの管理境界など、社内で明文化・共有済みだが本ドキュメントには再掲されていない前提に反していないか。クロスドキュメント依存を優先的に探す。たとえば本設計が別 PR や別 L2 設計書のマイルストーン・移行作業の完了を前提にしているのに、その依存関係がどちらのドキュメントにも優先度として明記されていない、といったケースである。「このチームなら当然分かるはず」という暗黙の共有知識が、実際には文書化も検証もされていないケースを疑う。
- **スケール**: ユーザー数・データ量・トラフィックが増えたとき破綻する設計か。前提となる規模が明記されているか。参照: `skills/pr-doc-review-pe/references/scale-and-failure-modes.md`。
- **想定外挙動**: 異常系・エッジケース・並行性・冪等性・失敗時の振る舞いが未定義でないか。「正常系しか書いていない」を疑う。参照: `skills/pr-doc-review-pe/references/scale-and-failure-modes.md`。
- **移行**: 移行期間・後方互換・データ移行順序・デュアルライト・新旧併存中の挙動が抜けていないか。
- **ロールバック**: 失敗時の切り戻し経路・不可逆操作が考慮されているか。「手動で対応」のみは不可。参照: `skills/pr-doc-review-pe/references/operational-design.md`。
- **可観測性**: 本番で壊れたとき root cause に到達できる metrics / logs / alerts があるか。「既存ダッシュボード参照」のみは不可。参照: `skills/pr-doc-review-pe/references/operational-design.md`。
- **未検討のライブラリ制約**: 採用技術・ライブラリに既知の制約があるのに、ドキュメントに一切言及がないケース。「書いてあることが間違っている」場合は軸2の技術的前提の事実誤りに分類し、「そもそも触れられていない」場合はこちらに分類する。
- **より良い設計の選択肢**: 原則 3 に従い、設計レベルでより良い代替がないか問う。参照: `skills/pr-doc-review-pe/references/alternatives-and-tradeoffs.md`。

プリモーテムを補助に使う。「6 ヶ月後に失敗するとしたら理由 3 件」を逆生成し、文書内で識別・緩和されているかを確認する。参照: `skills/pr-doc-review-pe/references/premortem-and-5whys.md`。

## Step 5: 自己検証ゲート

両 Pass の候補を統合し、以下を 1 回だけ通す。

1. **重複排除**: 同一 doc-path:line で重複する候補をまとめる。
2. **致命度ゲート**: 各候補が本番障害・データ不整合・移行失敗・ロールバック不能・API/データ契約の破壊のいずれかに直結するか判定する。直結しないものは除外し FN log に記録する。
3. **接地検証**: 各指摘が「具体的障害シナリオに接地しているか」「actionable / specific / verifiable か」を確認する。抽象的な提案・接地のない懸念は除外する。
4. **重複コメント除外**: 既存コメントと `$PR_BODY` で対処済みの指摘は除外する。
5. **Severity・軸タグ付与**: severity は次の基準で機械的に決める。`[nits]` は使わない。
   - `[must]`: 接地された障害シナリオが本番障害・データ不整合・移行失敗・ロールバック不能・契約破壊のいずれかに直結し、かつ文書内に恒久的な緩和策の記載がない。即時の障害だけでなく、サイレントな機能劣化や累積的なデータ不整合など間接的・遅延的に顕在化する場合も含む。
   - `[ask]`: 障害シナリオへの接地はできるが、並行稼働期間や Feature Flag などの一時的な緩和策が既に存在する、または著者の意図次第で致命度が変わる不確実性がある。
   - `[imo]`: 具体的障害シナリオに接地できて致命度ゲートは通過するが、即座の障害には直結しない改善提案。
   - `[good]`: 優れた判断。`### 良い点` 専用。
   - `[next]`: 今回スコープ外だが将来検討すべき。
   加えて各指摘に軸1/軸2/軸3のいずれかをタグ付けする。切り分けは原則5に従う。Pass 1 由来は軸1か軸2、Pass 2 由来は軸3になる。

## Step 6: 出力フォーマット

`▎` 記号や複数行 `>` の引用ブロックといった block quote は使わない。行番号は参照先として十分であり、引用文を別記する必要はない。

観点カバレッジ表の各セル・指摘の「現状」「あるべき姿」は目安 1〜2 文、目安 40 字程度に収める。厳格な足切りではないため、致命的な指摘が圧縮されて意味不明になるくらいなら長さを優先してよい。詳細な論証は指摘本文に書き、表は一目で状況がわかる要約に徹する。ドメイン固有の複合語などの専門用語は 1 指摘につき主要語 1 つまでに絞り、平易な言葉で言い換える。

```markdown
## PR #NNN レビュー: <タイトル>

**総評**: 2〜3 文で、ドキュメント種別・全体印象、そしてどの軸の指摘が最も致命的かという最重要懸念を書く。

### 観点カバレッジ
| 軸 | 状態 |
|------|------|
| 軸1: 形式 | <発見概要 1 文、目安 40 字以内 または N/A: 根拠 1 文> |
| 軸2: 論理矛盾・技術前提・データモデリング矛盾 | <発見概要 1 文、目安 40 字以内 または N/A: 根拠 1 文> |
| 軸3: 書いてない不文律・気づいていない致命的欠陥 | <発見概要 1 文、目安 40 字以内 または N/A: 根拠 1 文> |

### 指摘

**[must] (軸2)** `path/to/doc.md:42` — 論点タイトル (15 語以内)
現状: ドキュメントの記述と問題。致命的になりうる理由を障害シナリオで示す (目安 2 文以内)
あるべき姿: 修正の方向性 (目安 1〜2 文)

**[ask] (軸3)** `path/to/doc.md:15` — 論点タイトル
現状: 書いていない前提・検討されていない代替 (目安 2 文以内)
確認: 著者に問うべき具体的な質問 (1 文)

**[imo] (軸1)** `path/to/doc.md:50` — 論点タイトル
現状: ...
あるべき姿: ...

### 良い点
- `path/to/doc.md:line` — 優れた設計判断 (1 行)

### 検証ログ
Pass 1 (軸1・軸2) N 件 / Pass 2 (軸3) M 件 → 統合・致命度ゲート後 K 件
除外: X 件 (FN: <軸 / 指摘概要 目安 40 字以内 / 除外理由> 改行区切り。なしの場合は「なし」)
```

指摘事項がない場合は「指摘なし。Approve 推奨。」と書く。`[good]` は `### 良い点` 専用。
