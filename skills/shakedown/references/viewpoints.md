# shakedown 観点カタログ

使い方: SKILL.md の Step 2 で判定した機能タイプのセクション**だけ**を読む。全観点を毎回適用すると「壁」になり、チェックリスト疲労と形骸化を招く。各観点は実際のリリース事故の類型から抽出されている。

## 全タイプ共通

- **RCRCRC**(回帰対象を選ぶヒューリスティック): Recent(最近変えた箇所)、Core(中核導線)、Risky(元々危うい箇所)、Configuration-sensitive(設定依存)、Repaired(直したばかり)、Chronic(慢性的に壊れる箇所)。
- **兄弟コンポーネントの回帰**: 共有コンポーネントを変更した場合、同じものを使う「兄弟フォーム・兄弟画面」の初期値・挙動がデグレしていないか。無関係に見える修正の副作用はここに出る。
- **新旧パリティ**: 置き換え・リニューアルの場合、旧側にあった機能・文言・状態遷移ガードが新側に存在するか(壊れているのではなく「未実装」の欠落は差分レビューでは見えない)。旧画面の全アフォーダンスを新画面と突き合わせる。
- **ミラー対称性**: create/delete、add/remove、有効化/無効化など対方向の実装が対称か。「片方に足した分岐がもう片方にもあるか」を明示的に問う。
- **未実行経路**: 本番で一度も実行されたことのない経路はどれか。「正しいはずの半分」が実は動かない事故はここで起きる。
- **CRUD 最小セット**: 永続エンティティを触るなら「削除後の再読込」「並行更新」の最小チェック。
- **状態遷移**: ステータス enum・ワークフローがあるなら、不正遷移(手順飛ばし、二重送信、古い状態からのリプレイ)を 2〜3 個。新バージョンに旧バージョンと同等の遷移ガードがあるかも確認する。
- **先送り事項の追跡**: リリース時点で先送りされた方針判断は、日付付きのフォローアップ Issue になっているか。なっていなければ Wont-verify ではなく問題台帳の起票対象。

## カスタマー向け UI

- ユーザージャーニー形式の正常系 + 主要分岐(ゴールデンパスと一致させる)。
- **UI 5 状態セット**: ローディング / 空 / エラー / 成功 / 権限なし。UI を持つ変更には常時適用する。
- 初期描画(操作前)の見た目: 生 ID の露出、ラベル未解決、プレースホルダのまま表示。データが仕様通りかの確認では原理的に検出できない。
- 保存 → 離脱 → 再訪の一連操作: キャッシュ不整合(リロードすれば直るが遷移直後はズレる)。
- 操作中のレイアウトシフト・視覚的ジャンク(反復操作で顕在化する)。
- 隣接画面・旧画面との文言一致。

## 内部運用者向け管理画面

見た目の綺麗さより「事故らないか」を優先する。

- **破壊的操作の安全性**: 誤操作で本番データが壊れないか。確認ダイアログが誤クリックで閉じ、入力・選択が無言で失われないか。
- **使用中データへの編集**: 使用中・配信中のものを編集したら本番トラフィックに即時副作用が及ぶか。及ぶなら操作者にそれが見えるか。
- モードごとの有効な選択肢: ドロップダウン・ラジオの選択可能範囲がビジネスルールと一致するか。
- フロントバリデーションとバックエンド制約の同期: 欠けているとバックエンドの生エラーが運用者にそのまま露出する。
- update 側に create 側と同じクロスフィールド制約が再検証されているか(片側だけの制約は update から不変条件を破れる)。
- **無変更で保存**: 編集画面で何も変えずに保存する。全項目が同値で再送信されるため、全量更新の退行はこの最小ケースで最初に現れる。
- 完了後のブラウザバック・再送信で二重更新にならないか。
- **ラベルだけの UI**: このチェックボックス・ラベルは実際に何かを引き起こすか、説明するだけか。効果を持つように見えて持たない UI は運用判断を誤らせる。
- 権限・ロール境界: 見えてはいけないロールに見えていないか。
- アクション後の着地画面がエントリポイント別に意図通りか。
- 運用者が正しい判断をするための文脈情報(対象の現在状態、影響件数)が画面に足りているか。

## 純バックエンド / API

- 契約(proto・スキーマ)と実装の一致。後方・前方互換(古いクライアントからの呼び出し)。
- 境界値・不正入力の負系。境界値分析は順序のある入力(数値・件数・日付)のみに適用し、真偽値や不透明 ID には適用しない。
- 数値入力エッジ: 全角数字、小数点、意味的上限超過(101% など)、型境界オーバーフロー。「Unit/E2E でカバー済み」と書く前にテストの実在を確認する。
- べき等性・リトライ安全性: 二重送信、キュー再配達、リトライで二重作成されないか。
- **類似だが別物のクライアント取り違え**: 似た API クライアント・認証情報・環境が複数あるとき、正しい方を使っているか。単体テストのモックはこれを構造的に検出できないので、実環境での疎通確認をシナリオにする。
- 識別子フォーマットの前提: synthetic なテストデータではなく本番相当の実フォーマット(実 ID 形式)で通るか。前提ミスは「機能が実質的に配信不能」級の事故になる。
- 部分失敗からの回復: 途中で失敗したとき、どこまでがコミットされ、再実行で修復できるか。

## 非同期 / バッチジョブ

- **スケール検証は段階的に別セクション化する**: 数十件 → 数千件 → 本番相当件数。各段階で throughput・所要時間・再試行回数を記録する表を用意する。合格基準は DB で観測可能な数値で定義する(例: 総件数 == 作成済み件数、手動介入なしで完走)。
- 中断 → 再開の連続性: タイムアウト・デプロイによる中断後、続きから正しく再開するか。二重処理しないか。
- タイムアウト予算: scheduler の attempt deadline やジョブの実行予算をインフラ定義(terraform 等)から引用し、実測と突き合わせる。
- **進捗確認の turnkey クエリ**: 実行者が貼るだけで進捗・重複・残骸を確認できる SQL / コマンドをランブックに同梱する。実行者が自分でクエリを組み立てる前提にしない。
- ミラー方向の非対称(発行ジョブに対する取消ジョブなど)。
- 二重投入・並行実行の安全性。

## フィーチャーフラグ配下

- ON / OFF 両状態での動作。OFF 時に新コードが完全に不活性か。
- **フラグ参照箇所の全数確認**: 同じフラグが複数のサービス・デプロイロールから参照される場合、全箇所で設定が揃っているか(片側だけ ON の非対称状態で何が起きるか)。
- ロールバック: フラグを OFF に戻した後、UI とデータがクリーンに戻るか。ON 中に作られたデータが OFF 後の旧コードを壊さないか。
- 段階ロールアウト機構自体: 閾値、ターゲティングの一貫性(同一ユーザーが揺れないか)。
- 新旧共存境界の未文書化挙動: 旧経路が新画面から見えなくなる等の決定に明示的な理由付けがあり、旧経路が引き続き動作するか。

## テスト設計手法の適用条件

過剰適用を避けるための条件表。条件を満たさないなら使わない。

| 手法 | 適用条件 |
|---|---|
| 境界値分析・同値分割 | 順序のある入力(数値・件数・日付)のみ |
| デシジョンテーブル | 独立した条件が 3 つ以上絡むときのみ |
| ペアワイズ | 独立した設定軸が 3 つ以上あるときのみ。ワークフロー系には状態遷移テストの方が適合 |
| 状態遷移テスト | ステータス enum・ワークフローがあれば必須 |
| HICCUPPS | 仕様が曖昧・存在しないとき、「以前の挙動と一貫しているか」「類似機能と比べてどうか」を判断基準(オラクル)にする |
