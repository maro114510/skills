# ja-style-check

日本語テキストを次の 8 つの観点でレビューし、問題箇所と改善案を報告する。
対象はファイル形式を問わない。Markdown・プレーンテキスト・コードファイルのコメントすべてが対象となる。
人間が書いた文章・AI が生成した文章の両方が対象。

## 動作モードの確認

`$ARGUMENTS` に `--fix` が含まれる場合は **fix モード** で動作する。それ以外は **チェックモード**（レポートのみ）として動作する。

fix モードでは、ファイルパスは `--fix` を除いた残りの引数として解釈する。
fix モードの具体的な手順は末尾の「fix モード」セクションに記載する。チェック観点の定義はモードによらず共通である。

## 対象テキストの特定

`$ARGUMENTS` にファイルパスが指定されている場合はそのファイルを読む。
指定がない場合は、git で変更されているファイルのうち `.md` を対象とするか、ユーザーに確認する。

## チェック観点

対象テキストを以下の 8 観点で読み込み、問題を検出する。
問題が見つかった場合は、引用と行番号（特定できる場合）を示したうえで改善案を述べる。
問題がない観点は「問題なし」と短く記す。
同一箇所が複数の観点で問題を持つ場合は、最も本質的な観点で主に扱い、他の観点では一行の補足に留める。

---

### 観点 1：句点以外での改行

日本語の文は句点（。）で終えてから改行する。句点の前で改行されている箇所、または文の途中で意味なく改行されている箇所を指摘する。

ただし次の場合は改行を許容する：
- Markdown の見出し（`#`）・リスト項目（`-`・`*`・`1.`）・コードブロック（```` ``` ````）
- 長い URL や `bash` コマンドなど、分割できない要素
- テーブルの行

---

### 観点 2：括弧書きの多用

括弧書き（丸括弧「（）」・「()」）は、頻度と中身の種類の両面で判定する。
括弧書きが多い文章は、読み手が括弧の中身を後回しにして再読が必要になる。

**頻度による指摘**：括弧を使った補足が一段落または 3〜4 文の中で複数回現れる場合に指摘する。
1 文に括弧が 2 つ以上ある、または文末が括弧で終わっている箇所は、リズムが崩れるため特に強く指摘する。

**中身の種類による指摘**：次の種類が括弧に入っている場合は、出現回数に関わらず単発でも指摘する。読み手がその場で意味を取れないためである。
- 文書内参照（「§4.2」「§6.3 参照」「上記」など、別の場所を見ないと意味が取れないもの）
- 内部 ID・記号（「D-9」「S-02」「BLK-2」など、その文書固有の符号）
- コード識別子（変数名・関数名・ジョブ名・行番号・ファイルパス。観点 8 と重複する場合は観点 8 で主に扱う）

残してよい括弧は、原則として「初出語の定義（例：OMS（受注管理システム））」と「短い言い換え・列挙」に限る。
改善案として「括弧内の内容を独立した文として書き直す」「参照は地の文に溶かす（『詳細は後述する』など）」「括弧ごと削除できないか」を提案する。

---

### 観点 3：what の羅列・前置き・メタ実況

「何をするか」の説明・告知・自己言及が文章を占領していないかを確認する。ファイル形式や構文を問わずすべてのテキストが対象で、コードコメントも本文も区別しない。
読み手が本当に必要とするのは内容そのものであり、その内容を書く前に「これから何を書くか」を予告する文、自分の文章について語る文、読者に代わって結論を解釈してあげる文は原則として不要である。

**what の羅列**：「何をするか」をそのまま書いた記述を指摘する。
読み手が本当に必要とするのは「なぜそうするか」という意図であることが多い。

指摘パターンの例：
- 「〜を実行する」「〜を取得する」「〜を処理する」など動作の羅列
- 「ここで〜する」「以下に〜を行う」など手順の先読み説明
- 実装の詳細をそのまま日本語に翻訳したような記述（「ループを回して配列を走査する」など）

**前置き・告知（throat-clearing）**：内容を書く前に「何を書くか」を告知する文を指摘する。
告知自体は情報を持たず、読み手を前置きの分だけ遅らせる。

指摘パターンの例：
- 「まず〜について説明します」「以下に〜を示します」「〜について述べます」
- 「本節では〜を扱います」「このドキュメントでは〜を前提とします」
- 「〜を理解することが重要です」「〜ということがポイントです」
- 「〜とも言えます」「〜と言えるでしょう」（断言を避けた事実の迂回）

改善案：告知を省いて内容を直接書く。「まず X について説明します。X は〜」→「X は〜」。

**メタ実況・手取り足取り（meta-commentary / over-explanation）**：文章が自分自身について語る、または読者が自分で判断できることを代わりに解釈してあげる箇所を指摘する。

指摘パターンの例：
- 「以上を踏まえると」「これをまとめると」のあとに直前と同じ内容を繰り返す
- 「これにより〜が実現できます」（自明な結論を付け加える）
- 「つまり〜ということです」（前の文と同じ内容の言い換え）
- 「後述するように」「前述した通り」の多用（参照の乱用）

改善案：その言い換え・まとめ・解釈が前後の文を超えて新しい情報を加えているかを問う。加えていなければ削除する。

---

### 観点 4：自然言語による記述・曖昧語・根拠なき重要性宣言

**過度な箇条書き**・**曖昧語・弱表現**・**根拠なき重要性宣言**・**二項対立の乱用** の 4 点を確認する。

**過度な箇条書き**：箇条書きや番号リスト・表が過度に使われていて、散文で書いた方が読みやすくなる箇所を指摘する。

指摘の基準：
- 2 項目以下のリストで、文として続けて書ける内容
- リスト項目が主語と述語を持つ完全な文になっており、各項目の独立性が低い
- 段落の大半がリストで占められており、文章の流れが失われている

構造化フォーマット（リスト・表）が適切な場面（手順の列挙・比較など）では指摘しない。

**曖昧語・弱表現**：意味の範囲が広すぎて読み手が具体的な条件や基準を想定できない語句を指摘する。読み手が「これはどの範囲の話か？」「具体的には何をすればよいか？」と疑問を持つような記述が対象となる。

指摘の基準となる語句の例：「適切に」「適切な」「必要に応じて」「十分に」「基本的に」「可能なら」「考慮する」「担保する」「いい感じに」「ある程度」「なるべく」。ただしこれらは例示であり、リストに含まれない語句でも同様の問題があれば指摘する。
改善案として「条件・範囲・閾値を明記した書き直し例」を示す。

**根拠なき重要性宣言（vague declaratives）**：重要性・影響・深刻さを「宣言」するだけで、根拠や具体的な影響を示さない箇所を指摘する。読み手が「なぜ重要なのか」「どの程度の影響か」を問いたくなる記述が対象となる。

指摘パターンの例：
- 「これは非常に重要です」「影響は大きい」「課題は深刻である」「リスクは高い」
- 「〜が求められます」（誰に求められるか不明）
- 「〜は有益です」「〜には大きな価値がある」（根拠なし）

改善案：具体的な条件・数値・事例・影響範囲を示す。または宣言そのものを削除して事実だけを書く。

**二項対立の乱用**：「〜ではなく〜だ」という対比構造を使って意味なく回り道している箇所を指摘する。否定してから肯定する構造は、肯定だけで済む場合に回り道になる。

指摘パターンの例：
- 「問題は技術的なものではなく、人的なものである」→「問題は人的なものである」
- 「重要なのは速さではなく、品質だ」→「品質が重要だ」
- 「〜というわけではなく、〜ということだ」

改善案：肯定形で直接言う。否定してから言い直す構造を解体する。ただし、読者が誤解しやすい前提を覆す目的で否定している場合は残してよい。

### 観点 5：80 文字での折り返し

1 行が約 80 文字前後で機械的に折り返されている箇所を指摘する。
折り返しが意味の切れ目ではなく、文字数のみを根拠に挿入されていると判断できる場合に問題とする。

判断の手がかり：
- 連続する複数の行が 78〜82 文字付近で切れている
- 折り返し位置が句点・読点・接続詞のどこにも一致していない

テキストをファイルではなくインラインで受け取った場合など文字数の計測が困難なときは、意味の切れ目でない改行（観点1で検出した箇所）との重複として指摘し、その旨を一言添えればよい。

---

### 観点 6：段落構成の妥当性・文長のリズム

段落の構成と文長のリズムが読みやすいかを確認する。

**段落の構成**：
- **段落の長さ**：1 段落が 10 文を超えて読み続けることが困難になっていないか。長すぎる段落は、一つの段落が複数の話題を扱っているサインであることが多い。
- **段落の独立性**：一つの段落が一つの話題を扱っているか。話題の転換があるのに段落が分かれていない場合を指摘する。
- **段落の順序**：読み手が必要とする情報が、それを必要とするタイミングより前に提示されているか。前の段落で言及されていない概念が突然登場していないかを確認する。

**文長のリズム**：同じ長さの文が続くことで読み手が疲れる箇所を指摘する。

指摘パターンの例：
- **短文の連打（ドラマチックな断片化）**：短い文を連続させて人工的なリズムを作る。「〜だ。〜である。〜だ。」と続く箇所は、意図なく強調が繰り返されている印象を与える。
- **長文の連打**：長い文が続いて息継ぎできない段落。
- **箇条書き内の文長が揃いすぎている**：各項目が全て同程度の長さで並ぶと、リストが単調になる。

改善案：短文と長文を意図的に混ぜる。ドラマチックな断片化は一か所に絞るか解消する。

---

### 観点 7：初出語の定義・補足

テキスト中で初めて登場する専門用語・略語・固有名詞について、その場で定義や補足がなく読み手が意味を推測しなければならない箇所を指摘する。

チェック対象の例：
- 略語（例：CI/CD・DRY・LLM）—初出時に正式名称または概要が添えられているか
- ドメイン固有語（例：「スキル」が Claude Code のスキル機能を指す場合）—対象読者が知らない可能性がある場合に定義があるか
- 人名・組織名・プロジェクト名—文脈から推測できない場合に簡単な説明があるか

対象読者が当然知っていると想定できる一般的な技術用語（例：API・GitHub・JSON）は指摘しなくてよい。

---

### 観点 8：英語・コード識別子・記号参照の多用・主語の不明確さ

**日本語の自然言語で表現できるものは日本語で書く。誰が何をするかを明示する。** 文章が読み手ではなく実装やコードの方を向いていないか、また行為者が隠れて責任の所在が不明になっていないかを確認する。
英語のジャーゴン・コード識別子・内部記号は書き手の頭の中の地図であって、読み手がその場で理解できる言葉になっていないことが多い。受動態や無生物主語も同様に、「誰が」を隠す。

**英語・カタカナ語のジャーゴン**：日本語で言い換えられるのに英語表現のまま置かれている語。
  例：「fire-and-forget」→「完了を待たない方式」、「roll-forward」→「前進対応」、「ブラックアウト」→「販売停止」。
  日本語に定着し、言い換えるとかえって不正確になる語（API・OAuth・Webhook など）は指摘しない。

**コード識別子の本文への混入**：変数名・関数名・ジョブ名・ファイルパス・行番号・生のブール式（`foo != nil && bar == ""` など）が、読み手向けの文章にそのまま現れている箇所。
  これらは振る舞いを日本語で記述し、出典が必要なら本文ではなく末尾の根拠セクションへ追い出すよう提案する。

**内部 ID・記号**：「D-9」「S-02」「BLK-2」など、その文書や別資料の符号。それ単体で読み手が意味を取れない場合に指摘する。

**文書内・文書間参照**：「§4.2」「UC1 §5.8」など、参照先を見ないと意味が取れない括弧内・文中の参照。

**主語の不明確さ・受動態の過用（hidden actors）**：誰が行動するかが隠れている箇所を指摘する。行為者が不明なままだと、責任の所在・作業者・適用タイミングが読み取れない。

指摘パターンの例：
- **受動態の連続**：「〜される」「〜られる」「〜が行われる」が文をまたいで続く。誰がそれをするのかが隠れている。
- **無生物主語**：「本設計は〜を実現する」「この機能は〜を提供する」「本ドキュメントは〜を定義する」—設計・機能・ドキュメントは人間の手を借りて初めて動く。「誰が」を問いかけてみる。
- **行為者の省略**：「〜が必要です」「〜が求められます」「〜とみなされます」—誰が必要とし、誰が求め、誰がみなすのかが不明。
- **判断の隠蔽**：「〜と判断される」「〜は適切とされる」—誰の判断か、何を根拠にしているかが不明。

改善案：行為者を明示する。「〜が行われる」→「チームが〜を行う」。「〜が必要です」→「開発者が〜する必要がある」。能動形にする。ただし、行為者が一般利用者・自動処理・不特定多数など特定できない性質のものであれば受動態でも構わない。

判定の手がかり（観点 8 全体）：
- **音読テスト**：その箇所を声に出して読んで、日本語の文として意味が通るか。識別子や記号で詰まるなら言い換える。
- **読者テスト**：その記号・英語・参照を知らない読み手が、その場で意味を取れるか。取れないなら指摘する。
- **行為者テスト**：「誰が」を問いかけて答えが出るか。出ないなら指摘する。

ただし、コードブロック・表の中で実際の識別子を示すことが目的の箇所（API 名の一覧、設定値の対応表など）は対象外とする。問題は「読み手向けの地の文に紛れ込んでいる」ことであって、識別子を示すこと自体ではない。

## 出力フォーマット

観点ごとにセクションを立て、問題があれば次の形式で報告する：

```
### 観点N：〈観点名〉

**問題なし** ／ または

**[行番号 or 箇所の引用]**
問題の説明と、なぜ問題なのかの理由。

改善案：
> （改善後の文例）
```

最後に「総評」を 2〜3 文で添える。問題の多さと深刻度（読みにくさへの影響度）の全体感を伝える。

深刻度を評価する際は、次の状態を過小評価しないこと。これらが文章全体にわたって頻出する場合、読みにくさへの影響度は「高」と判断する。
- 英語・カタカナ語のジャーゴンやコード識別子が地の文に頻出し、日本語として読み通せない（観点 8）
- 読み手がその場で意味を取れない記号・内部 ID・文書内参照が繰り返し現れる（観点 2・観点 8）
- 多くの文が括弧書きの補足を抱えており、再読しないと意味が取れない（観点 2）
- 前置き・メタ実況・手取り足取りが文章の大半を占め、内容が薄く見える（観点 3）
- 行為者が全体を通じて隠れており、誰が何をするかを読み取れない（観点 8）

数件の局所的な指摘で全体は読みやすい場合と、文章全体が実装寄りで読み通せない場合とを取り違えないこと。後者を「影響度 低〜中」と評価してはならない。

## fix モード

`--fix` が指定された場合のみ、「出力フォーマット」のレポートを出力した後に以下の手順で修正を適用する。

### ステップ 1：git 安全確認

対象ファイルに対して `git status --porcelain` を実行し、未コミットの変更（M・A・D・?? など）があるファイルが対象に含まれる場合は次のメッセージを出力してユーザーに確認を求める：

```
[警告] 以下のファイルに未コミットの変更があります：
  - path/to/file.md

修正を適用するとこれらの変更に上書きが入ります。続行しますか？ [y/N]
```

ユーザーが N（またはデフォルト）を入力した場合は修正を中止して終了する。
git が使えない環境（リポジトリ外など）ではこのステップをスキップする。

### ステップ 2：機械的修正の自動適用

以下の観点で検出した問題は確認なしにファイルへ直接適用する。文意は変わらないため事前確認は不要である。

**観点 1（句点以外での改行）**

句点（。）の前で改行されている行を次の行と結合する。

ただし次の場合は結合しない：
- 次の行が Markdown 見出し（`#`）・リスト項目（`-`・`*`・`1.`）・コードブロック（```` ``` ````）の開始行
- 長い URL やシェルコマンドを含む行
- テーブル行（`|` で始まる行）

**観点 5（80 文字での折り返し）**

78〜82 文字付近で機械的に折り返されていると判断した行を前後で結合する。判断基準は観点 5 の検出基準と同じ（折り返し位置が句点・読点・接続詞と一致しない）。

結合後の行が 200 文字を超える見込みがある場合は自動適用せず、ステップ 3 の確認ありフローに含める。

自動適用した修正がある場合は、適用した件数と箇所を一覧表示する。

### ステップ 3：文意を変える修正の確認と適用

観点 2〜4・6〜8 で検出した問題について、修正案を番号付きリストで一覧表示する：

```
以下の修正案があります：
