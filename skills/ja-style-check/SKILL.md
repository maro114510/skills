# ja-style-check

日本語テキストを次の観点でレビューし、決定的に直せる問題はその場で修正する。
対象はファイル形式を問わない。Markdown・プレーンテキスト・コードファイルのコメントすべてが対象で、人間が書いた文章・AI が生成した文章の両方を扱う。

## 動作モード

`$ARGUMENTS` の先頭が `report` または `--report` のときは **report モード**で動作する。report モードではファイルを変更せず、レポートのみを出力する。それ以外は **修正モード（デフォルト）** で動作する。

report モードでは、ファイルパスは `report` / `--report` を除いた残りの引数として解釈する。
チェック観点の定義はモードによらず共通である。修正モードの具体的な手順は末尾の「修正モード（デフォルト）」セクションに記載する。

## 対象テキストの特定

`$ARGUMENTS` にファイルパスが指定されている場合はそのファイルを読む。
指定がない場合は、git で変更されているファイルのうち `.md` を対象とするか、ユーザーに確認する。

## チェック観点

対象テキストを以下の観点で読み込み、問題を検出する。
問題が見つかった場合は、引用と行番号（特定できる場合）を示したうえで改善案を述べる。
問題がない観点は「問題なし」と短く記す。
同一箇所が複数の観点で問題を持つ場合は、最も本質的な観点で主に扱い、他の観点では一行の補足に留める。

---

### 観点 1：句点以外での改行

日本語の文は句点（。）で終えてから改行する。句点の前で改行されている箇所、または文の途中で意味なく改行されている箇所を指摘する。

ただし次の場合は改行を許容する：
- Markdown の見出し（`#`）・リスト項目（`-`・`*`・`1.`）・コードブロック（```` ``` ````）
- 長い URL や `bash` コマンドなど、分割できない要素
- テーブルの行

---

### 観点 2：括弧書きの多用

括弧書き（丸括弧「（）」「()」）が多い文章は、読み手が中身を後回しにして再読を強いられる。頻度で判定する。
括弧を使った補足が一段落または 3〜4 文の中で複数回現れる場合に指摘する。1 文に括弧が 2 つ以上ある、または文末が括弧で終わっている箇所は、リズムが崩れるため特に強く指摘する。

残してよい括弧は「初出語の定義（例：OMS（受注管理システム））」のみとする。語の意味・正式名称・日本語訳を示す括弧が定義であり、単位・数値・属性・タイミング・動作の補足（例：`（単位：円）`、`（自動処理）`）は削除または変換の対象とする。
括弧内が文書内参照・内部 ID・コード識別子の場合は、それ単体で意味が取れないため観点 8 で扱う。

改善案：括弧内を独立した文に書き直す／参照は地の文に溶かす／括弧ごと削除できないか検討する。

---

### 観点 3：what の羅列・前置き・メタ実況

「何をするか」の説明・告知・自己言及が文章を占領していないかを確認する。ファイル形式や構文を問わずすべてのテキストが対象で、コードコメントも本文も区別しない。
読み手が必要とするのは内容そのものであり、内容の前に「これから何を書くか」を予告する文、自分の文章について語る文、読者に代わって結論を解釈する文は原則として不要である。

**what の羅列**：「何をするか」をそのまま書いた記述を指摘する。読み手が必要とするのは「なぜそうするか」という意図であることが多い。

指摘パターンの例：
- 「〜を実行する」「〜を取得する」「〜を処理する」など動作の羅列
- 「ここで〜する」「以下に〜を行う」など手順の先読み説明
- 実装の詳細をそのまま日本語に翻訳したような記述（「ループを回して配列を走査する」など）

**前置き・告知**：内容の前に「何を書くか」を告知する文を指摘する。告知自体は情報を持たず、読み手を遅らせる。

指摘パターンの例：
- 「まず〜について説明します」「以下に〜を示します」「〜について述べます」
- 「本節では〜を扱います」「このドキュメントでは〜を前提とします」
- 「〜を理解することが重要です」「〜ということがポイントです」
- 「〜とも言えます」「〜と言えるでしょう」（断言を避けた事実の迂回）

改善案：告知を省いて内容を直接書く。「まず X について説明します。X は〜」→「X は〜」。

**メタ実況・手取り足取り**：文章が自分自身について語る、または読者が自分で判断できることを代わりに解釈する箇所を指摘する。

指摘パターンの例：
- 「以上を踏まえると」「これをまとめると」のあとに直前と同じ内容を繰り返す
- 「これにより〜が実現できます」（自明な結論を付け加える）
- 「つまり〜ということです」（前の文の言い換え）
- 「後述するように」「前述した通り」の多用（参照の乱用）

改善案：その言い換え・まとめ・解釈が前後の文を超えて新しい情報を加えているかを問う。加えていなければ削除する。

---

### 観点 4：自然言語による記述・曖昧語・根拠なき重要性宣言

**過度な箇条書き**・**曖昧語・弱表現**・**根拠なき重要性宣言**・**二項対立の乱用** の 4 点を確認する。

**過度な箇条書き**：箇条書きや番号リスト・表が過度に使われ、散文で書いた方が読みやすくなる箇所を指摘する。

指摘の基準：
- 2 項目以下のリストで、文として続けて書ける内容
- リスト項目が主語と述語を持つ完全な文になっており、各項目の独立性が低い
- 段落の大半がリストで占められ、文章の流れが失われている

構造化フォーマットが適切な場面（手順の列挙・比較など）では指摘しない。

**曖昧語・弱表現**：意味の範囲が広すぎて読み手が具体的な条件や基準を想定できない語句を指摘する。「これはどの範囲の話か」「具体的に何をすればよいか」と疑問を持つ記述が対象。

指摘の基準となる語句の例：「適切に」「適切な」「必要に応じて」「十分に」「基本的に」「可能なら」「考慮する」「担保する」「いい感じに」「ある程度」「なるべく」。これらは例示であり、同様の問題があればリスト外の語句でも指摘する。
改善案として「条件・範囲・閾値を明記した書き直し例」を示す。

**根拠なき重要性宣言**：重要性・影響・深刻さを「宣言」するだけで、根拠や具体的な影響を示さない箇所を指摘する。「なぜ重要か」「どの程度の影響か」を問いたくなる記述が対象。

指摘パターンの例：
- 「これは非常に重要です」「影響は大きい」「課題は深刻である」「リスクは高い」
- 「〜が求められます」（誰に求められるか不明）
- 「〜は有益です」「〜には大きな価値がある」（根拠なし）

改善案：具体的な条件・数値・事例・影響範囲を示す。または宣言を削除して事実だけを書く。

**二項対立の乱用**：「〜ではなく〜だ」という対比構造で意味なく回り道している箇所を指摘する。否定してから肯定する構造は、肯定だけで済む場合に回り道になる。

指摘パターンの例：
- 「問題は技術的なものではなく、人的なものである」→「問題は人的なものである」
- 「重要なのは速さではなく、品質だ」→「品質が重要だ」
- 「〜というわけではなく、〜ということだ」

改善案：肯定形で直接言う。ただし、読者が誤解しやすい前提を覆す目的で否定している場合は残してよい。

---

### 観点 5：80 文字での折り返し

1 行が約 80 文字前後で機械的に折り返されている箇所を指摘する。
折り返しが意味の切れ目ではなく、文字数のみを根拠に挿入されていると判断できる場合に問題とする。

判断の手がかり：
- 連続する複数の行が 78〜82 文字付近で切れている
- 折り返し位置が句点・読点・接続詞のどこにも一致していない

テキストをインラインで受け取った場合など文字数の計測が困難なときは、意味の切れ目でない改行（観点 1 で検出した箇所）との重複として指摘し、その旨を一言添える。

---

### 観点 6：段落構成の妥当性・文長のリズム

段落の構成と文長のリズムが読みやすいかを確認する。

**段落の構成**：
- **段落の長さ**：1 段落が 10 文を超えて読み続けることが困難になっていないか。長すぎる段落は、一つの段落が複数の話題を扱っているサインであることが多い。
- **段落の独立性**：一つの段落が一つの話題を扱っているか。話題の転換があるのに段落が分かれていない場合を指摘する。
- **段落の順序**：読み手が必要とする情報が、それを必要とするタイミングより前に提示されているか。前の段落で言及されていない概念が突然登場していないか。

**文長のリズム**：同じ長さの文が続いて読み手が疲れる箇所を指摘する。

指摘パターンの例：
- **短文の連打（ドラマチックな断片化）**：短い文を連続させて人工的なリズムを作る。「〜だ。〜である。〜だ。」と続く箇所は、意図なく強調が繰り返されている印象を与える。
- **長文の連打**：長い文が続いて息継ぎできない段落。
- **箇条書き内の文長が揃いすぎている**：各項目が同程度の長さで並び、リストが単調になる。

改善案：短文と長文を意図的に混ぜる。ドラマチックな断片化は一か所に絞るか解消する。

---

### 観点 7：初出語の定義・補足

テキスト中で初めて登場する専門用語・略語・固有名詞について、その場で定義や補足がなく読み手が意味を推測しなければならない箇所を指摘する。

チェック対象の例：
- 略語（例：CI/CD・DRY・LLM）—初出時に正式名称または概要が添えられているか
- ドメイン固有語（例：「スキル」が Claude Code のスキル機能を指す場合）—対象読者が知らない可能性がある場合に定義があるか
- 人名・組織名・プロジェクト名—文脈から推測できない場合に簡単な説明があるか

対象読者が当然知っていると想定できる一般的な技術用語（例：API・GitHub・JSON）は指摘しなくてよい。

---

### 観点 8：英語・コード識別子・記号参照の多用・主語の不明確さ

**日本語の自然言語で表現できるものは日本語で書く。誰が何をするかを明示する。** 文章が読み手ではなく実装やコードの方を向いていないか、また行為者が隠れて責任の所在が不明になっていないかを確認する。
英語のジャーゴン・コード識別子・内部記号は書き手の頭の中の地図であって、読み手がその場で理解できる言葉になっていないことが多い。受動態や無生物主語も同様に「誰が」を隠す。

**英語・カタカナ語のジャーゴン**：日本語で言い換えられるのに英語表現のまま置かれている語。
  例：「fire-and-forget」→「完了を待たない方式」、「roll-forward」→「前進対応」、「ブラックアウト」→「販売停止」。
  日本語に定着し、言い換えるとかえって不正確になる語（API・OAuth・Webhook など）は指摘しない。

**コード識別子の本文への混入**：変数名・関数名・ジョブ名・ファイルパス・行番号・生のブール式（`foo != nil && bar == ""` など）が読み手向けの文章にそのまま現れている箇所。振る舞いを日本語で記述し、出典が必要なら本文ではなく末尾の根拠セクションへ追い出すよう提案する。

**内部 ID・記号、文書内・文書間参照**：「D-9」「S-02」「§4.2」「UC1 §5.8」など、その文書固有の符号や、参照先を見ないと意味が取れない参照。それ単体で読み手が意味を取れない場合に指摘する。

**主語の不明確さ・受動態の過用**：誰が行動するかが隠れている箇所を指摘する。行為者が不明だと、責任の所在・作業者・適用タイミングが読み取れない。

指摘パターンの例：
- **受動態の連続**：「〜される」「〜られる」「〜が行われる」が文をまたいで続く。誰がそれをするのかが隠れている。
- **無生物主語**：「本設計は〜を実現する」「この機能は〜を提供する」「本ドキュメントは〜を定義する」—設計・機能・ドキュメントは人間の手を借りて初めて動く。「誰が」を問いかける。
- **行為者の省略**：「〜が必要です」「〜が求められます」「〜とみなされます」—誰が必要とし、求め、みなすのかが不明。
- **判断の隠蔽**：「〜と判断される」「〜は適切とされる」—誰の判断か、何を根拠にしているかが不明。

改善案：行為者を明示し能動形にする。
- 「〜が行われる」→「チームが〜を行う」
- 「〜が必要です」→「開発者が〜する必要がある」

ただし、行為者が一般利用者・自動処理・不特定多数など特定できない性質のものであれば受動態でも構わない。

判定の手がかり：
- **音読テスト**：声に出して読んで日本語の文として意味が通るか。識別子や記号で詰まるなら言い換える。
- **読者テスト**：その記号・英語・参照を知らない読み手が、その場で意味を取れるか。
- **行為者テスト**：「誰が」を問いかけて答えが出るか。

ただし、コードブロック・表の中で実際の識別子を示すことが目的の箇所（API 名の一覧、設定値の対応表など）は対象外とする。問題は「読み手向けの地の文に紛れ込んでいる」ことであって、識別子を示すこと自体ではない。

---

### 観点 9：実装の写経（処理・分岐を地の文に書く）

1 文・1 段落が処理構造をそのままなぞっていないかを確認する。観点 8 が個々の語・識別子を局所的に見るのに対し、観点 9 は文の構造そのものが実装の写経になっていることを問題にする。

強く指摘するサイン：
- 1 文に識別子・英語・記号が複数混在し、日本語として読み下せない
- 条件分岐や論理を地の文に書いている（「`flag` が true なら〜、false なら〜」「A かつ B のとき〜」など）
- 「〜を処理する」「〜のフラグを立てる」など、処理の言葉で実際の振る舞いをぼかしている

改善案：その文が結局 **何をするか** を、識別子も分岐も使わず一文の自然な日本語で言い直す。「`isPaid` が true のとき決済済みフラグを立てる」→「支払いが完了したら注文を確定する」。

## 出力フォーマット（report モード）

report モードでは、観点ごとにセクションを立て、問題があれば次の形式で報告する：

```
### 観点N：〈観点名〉

**問題なし** ／ または

**[行番号 or 箇所の引用]**
問題の説明と、なぜ問題なのかの理由。

改善案：
> （改善後の文例）
```

最後に「総評」を 2〜3 文で添える。問題の多さと深刻度（読みにくさへの影響度）の全体感を伝える。

次が文章全体に頻出する場合は、読みにくさへの影響度を「高」と判断する。過小評価しないこと。
- ジャーゴン・コード識別子が地の文に頻出し、日本語として読み通せない（観点 8）
- 意味の取れない記号・内部 ID・参照が繰り返し現れる（観点 8）
- 多くの文が括弧の補足を抱え、再読しないと意味が取れない（観点 2）
- 前置き・メタ実況が文章の大半を占める（観点 3）
- 行為者が全体を通じて隠れている（観点 8）
- 文が実装の写経になっている（観点 9）

数件の局所的な指摘で全体は読みやすい場合と、文章全体が実装寄りで読み通せない場合とを取り違えないこと。後者を「影響度 低〜中」と評価してはならない。

## 修正モード（デフォルト）

`report` / `--report` が指定されていない場合、検出した問題のうち**決定的に直せる修正**をファイルへ直接適用する。
**推論が必要な修正**は勝手に書き換えず、修正提案として報告する。

### 自動適用と報告のみの切り分け

**判定の原則**：修正後のテキストが、元のテキストに既に書かれている情報だけで一意に決まるなら自動適用する。
定義の中身・隠れた行為者・具体的な閾値など、元テキストにない情報の補完や推測が必要なら適用せず報告する。
同じ観点でも箇所ごとにこの原則で切り分ける。迷う箇所は適用せず報告に回す（安全側に倒す）。

**自動適用する修正（決定的）**：
- **観点 1**：句点前で改行された行を結合する。観点 1 に挙げた例外行は結合しない。
- **観点 5**：機械的に折り返された行を結合する。結合後が 200 文字を超える見込みなら報告に回す。
- **観点 2**：定義以外の括弧を削除、または中身を地の文へ移す（中身が既に本文にあり語義を補わない場合）。
- **観点 3**：情報を持たない前置き・告知・メタ実況の文を削除する。
- **観点 4**：根拠なき重要性宣言の削除、二項対立の肯定形化、過度な箇条書きの散文化。
- **観点 8**：英語ジャーゴンを定着した日本語訳へ、コード識別子を既出の振る舞い記述へ言い換える。
- **観点 9**：実装の写経を自然な日本語へ言い直す。

**報告のみにとどめる修正（推論が必要）**：
- **観点 4**：曖昧語の具体化。
- **観点 6**：段落の再構成・順序入れ替え・文長リズムの調整。
- **観点 7**：初出語の定義追加。
- **観点 8**：隠れた主語の補完。
- **観点 9**：意図が本文から決まらない実装の写経の言い直し。

### 手順

1. **自動適用**：決定的な修正を Edit ツールでファイルへ直接適用する。

2. **括弧ゼロ確認（観点 2 の後処理）**：括弧に関する修正を適用したあと対象ファイルを再読する。定義以外の括弧が残っていれば、決定的に消せるものは追加で削除し、推論が必要なものは報告に回す。決定的に消せる範囲の非定義括弧がゼロになるまで繰り返す。件数が減らなくなったら打ち切る。

3. **修正サマリーの出力**：全修正が完了したら次の形式で報告する。

```
修正完了：
- 自動適用：N 件
  - 観点1（改行）: A 件
  - 観点2（括弧）: B 件
  - …
- 要手動対応（推論が必要なため未適用）：M 件
  1. [観点7 / 行XX] 「OMS」— 初出だが定義なし。正式名称を本文から決められない。
  2. [観点8 / 行YY] 「〜が行われる」— 行為者が不明。誰が行うかを本文から決められない。
  …
```

要手動対応の各項目には、箇所の引用と「なぜ自動修正できないか」を一行添える。
