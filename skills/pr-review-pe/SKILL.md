# pr-review-pe

PR の diff を読み、PE が本当に気にすることを指摘する。AI が書いたコードに特有のリスクを
重点チェックしながら、8つの観点で構造的・論理的・セキュリティ的な問題を洗い出す。

## Step 1: PR 特定

`$ARGUMENTS` を解析する:

- 数値のみ（例: `123`）→ そのまま PR 番号として使用
- GitHub URL（`/pull/123` を含む）→ URL から番号を抽出
- 引数なし → 現在のブランチの PR を `gh pr view --json number` で取得

PR が特定できない場合は次のように伝えて停止する:
「現在のブランチ `<branch名>` に PR が見つかりません。PR 番号または URL を引数で指定してください（例: `9` / `https://github.com/org/repo/pull/9`）。」
（gh コマンドが一時障害で失敗した場合も同様に停止し、ユーザーに手動で PR 番号を指定するよう案内する。）

## Step 2: データ収集（並列実行）

```bash
# PR メタ情報
gh pr view $PR_NUMBER --json title,body,author,baseRefName,headRefName,additions,deletions,changedFiles

# 差分（ハルシネーション防止の基盤）
gh pr diff $PR_NUMBER

# 既存コメント・レビュー（重複防止）
gh pr view $PR_NUMBER --json comments,reviews
```

diff を受け取ったら以下を抽出・記録する:

- **依存関係の変更**: `package.json`, `go.mod`, `Cargo.toml`, `requirements.txt`, `pyproject.toml` などへの追加パッケージ名
- **新しいテストファイル**: PR に含まれるテストファイルの一覧
- **変更ファイルの言語・フレームワーク**: レビュー観点のキャリブレーションに使う

## Step 3: 8観点でレビュー

diff を読み、以下の8観点で問題を探す。**各指摘は必ず diff の該当コードを引用してから行う**
（引用できない = diff に存在しない = 指摘してはならない）。

既存コメントで既に指摘されている内容は重複して指摘しない。
PR description でユーザー自身が説明・対処済みの問題も指摘しない。

---

### 観点 1: 正確性（最優先）

> 「このコードは PR が解決しようとした問題を実際に解決しているか？」

PR description に書かれた目的・仕様と実装が一致しているかを能動的に確認する。

確認すること:

- ビジネスロジックの正確さ: 条件分岐・計算式・状態遷移が仕様と一致しているか
- エッジケースの処理: `null/nil/undefined`・空配列・0・負数・境界値（MaxInt等）・空文字列が正しく処理されているか
- PR description が謳う機能・修正が diff に実際に存在しているか

**AI特有リスク**: 同一AIが実装とテストを生成した場合、テストが実装と同じ誤った前提を共有する「確認バイアス」が起きる。テストのカバーしているケースと実装の前提を照合する。

---

### 観点 2: アーキテクチャ

- 責務分離: 単一責任原則・関心の分離が守られているか
- 依存関係の方向: 下位レイヤーが上位レイヤーに依存していないか（循環依存）
- 設計パターンの適切さ: 不必要な抽象化・設計パターンの過剰適用がないか
- Over-engineering の検出: 仮想的な将来要件のための不要な複雑性が追加されていないか

---

### 観点 3: スケーラビリティ

- N+1 クエリ: ループ内でのクエリ発行・関連データの一括取得漏れ
- ボトルネック: 同期ブロッキング処理・大量データのメモリロード
- キャッシュ設計: 有効期限・バスタリング・コールドスタート問題
- データ量増加時の挙動: ページネーションなしの全件取得・インデックス欠如

---

### 観点 4: セキュリティ（AI特有リスクを含む）

基本確認:

- 入力検証: 未検証の外部入力の使用、型強制の欠如
- 認証・認可: 保護すべきエンドポイント・リソースへのアクセス制御の欠如
- 機密情報の扱い: ハードコードされたシークレット・ログへの機密値出力
- インジェクション: SQLi・コマンドインジェクション・XSS・パストラバーサル

**AI特有 — ハルシネーション依存パッケージ**:

Step 2 で抽出した新規依存パッケージを対象に存在確認を実行する:

```bash
# npm パッケージの場合
npm view <package-name> version

# PyPI パッケージの場合
pip show <package-name>

# Go モジュールの場合
go list -m <module-path>@latest
```

コマンドが失敗した場合、またはコマンドの結果からレジストリ上の存在が確認できない場合は WebFetch でレジストリ（npmjs.com, pypi.org, pkg.go.dev）を確認する。

**判定の注意点**:
- `npm view <pkg>` が 404 → パッケージが npm に存在しない
- `pip show <pkg>` が "not found" → **ローカル未インストールを意味するだけで PyPI 非存在の証明にはならない**。必ず WebFetch で pypi.org を確認する
- `go list -m <mod>@latest` がエラー → WebFetch で pkg.go.dev を確認する

存在しないパッケージは [must] として報告する（名前のスクワッティング攻撃のリスクがあるため）。

**AI特有 — 非推奨・CVE対象API**: 使用しているAPIが学習データカットオフ以降に廃止・脆弱性指定されていないか確認する（主要ライブラリのメジャーバージョン変更に特に注意）。

---

### 観点 5: API 設計

- 後方互換性の破壊: 既存の公開インターフェース・型・パラメータの変更
- インターフェースの明確さ: 関数名・引数・戻り値の型が意図を十分に表現しているか
- バージョニング: API バージョンの扱い、deprecation の通知

---

### 観点 6: エラーハンドリング・並行安全性・リソース管理

**エラーハンドリング**:

- エラーの握りつぶし: error を無視している箇所
- エラー情報の伝播: 根本原因が失われたエラーラッピング
- リトライ設計: べき等性のない操作への無制限リトライ
- タイムアウト: 外部呼び出しにタイムアウト設定がない

**リソース管理（AI特有の見落としポイント）**:

- エラーパスでのリソース解放漏れ: DB接続・ファイルハンドル・ゴルーチン・ミューテックス
- `defer close()` / `using` / `try-finally` の欠如
- ゴルーチンリーク: 受信側のいないチャネル送信・WaitGroup の未完了

**並行安全性（AI頻出の見落とし）**:

- キャッシュ読み取り→書き戻しがアトミックでない（check-then-act パターン）
- スレッドセーフでないコレクションへの並行アクセス
- グローバル状態・シングルトンへの並行書き込み
- ミューテックスのデッドロック可能性

---

### 観点 7: 運用性

- ログ: 適切な構造化ログ・ログレベル・PII の非出力
- メトリクス: 可観測性の確保（リクエスト数・エラー率・レイテンシ）
- デプロイ影響範囲: マイグレーションの後方互換性・機能フラグ・段階的デプロイの要否
- 設定の外部化: ハードコードされた環境依存値がないか

---

### 観点 8: テスト品質（AI特有）

テストが PR に含まれる場合のみ評価する。

- **確認バイアスのチェック**: テストが実装と同じ誤った前提（同じ境界値の誤解・同じエッジケース見落とし）を共有していないか
- **ハッピーパス偏重**: 正常系テストのみでエラーパス・null 入力・境界値テストが欠如していないか
- **モック過剰**: 結合テストとしての意味を失うほどモックが多用されていないか
- **テストの有効性**: テストが失敗すべき条件で実際に失敗するか（自明に通過するだけのテストでないか）

**重要度の目安**:
- テストがテスト対象コードを一切呼び出していない（ハンドラ未呼び出し・メソッド未実行など）場合は [must]（テストなしと等価）
- PR にテストが全く含まれていない場合、新規追加した機能に相当するテストが存在しないことを [imo] として指摘してよい
- エッジケースやエラーパスの欠落・ハッピーパス偏重は [imo]

---

### 指摘前必須確認: 既存パターン照合（書く前に確認する）

**各指摘を書く前に**必ず実行する。書いてから確認するのではなく、**確認してから書く**。

気になる実装を見つけたら、タグを付ける前に次を問う:

> 「同じパターンが既存の類似ファイルにあるか？」

- **YES（確認できた）→ この指摘の検討をここで完全に中止する。**  
  タグ・本文・注記・将来改善提案・設計確認、いかなる形でも出力しない。  
  「慣習踏襲のため修正不要だが〜」のような付記も禁止。何も書かずに次の候補へ進む。
- **NO（1 件も一致しない）→ 次の重要度判断へ進む。**

確認対象と方法:

- GitHub Actions: 同命名ワークフロー（`*-release-publish.yaml` など）を 2〜3 件確認
- Go ハンドラ / クエリ / E2E テスト: 同ファイル内または同ディレクトリの既存実装を 2〜3 件確認
- IaC / 設定: 同種リソースの既存定義を 2〜3 件確認

2〜3 件で一致を見たら照合完了。全ファイルを網羅する必要はない。

---

### 重要度の判断基準

| タグ | 基準 | 対応 |
|------|------|------|
| [must] | 本番で問題が起きる / API 互換性を破壊 / セキュリティリスク / 仕様と実装の不一致 | 修正必須 |
| [imo] | 改善が望ましいがブロッカーではない | 修正任意 |
| [nits] | 原則スキップ — PE 観点では命名・スタイルの細かい指摘は行わない | — |
| [ask] | 設計判断に影響する意図が PR description から読めない場合のみ。ただし既存パターン照合で一致が確認できた事項は [ask] も不可（「設計が意図的か確認したい」も同様に禁止） | 回答必須 |
| [good] | 特に優れた設計判断 | — |
| [next] | 今回スコープ外の将来検討すべき設計課題 | 修正不要 |

## Step 3.5: 破壊シミュレーション

各変更に対して「このコードを壊すとしたら何をするか？」を能動的に想定する。

以下のシナリオを1つずつ当てはめ、防御されていないシナリオを指摘候補に追加する:

1. **並行アクセス**: 同一関数を複数スレッド/ゴルーチンから同時に呼んだら何が起きるか
2. **null/nil 入力**: 引数・外部入力・DB レスポンスが null/nil の場合の全パスをトレース
3. **ネットワーク切断**: 外部 API への呼び出しが途中で失敗した場合、トランザクションは巻き戻るか
4. **大量データ**: 1000倍のデータが来た場合、どのパスが OOM やタイムアウトを引き起こすか
5. **悪意ある入力**: 最大長文字列・制御文字・SQL特殊文字・パストラバーサル文字を入力したら何が起きるか

防御が確認できたシナリオは頭の中でのみ記録する（最終出力への箇条書きは不要）。防御が不明・欠如しているシナリオは Step 3 の指摘候補に追加し、[must] または [ask] として扱う。5シナリオを個別にリストアップする箇条書きを最終出力に含めてはならない。

**「部分的に防御されている」場合の扱い**: 全パスではなく一部のパスしか防御されていない（例: 状態更新は防御しているがリトライは止まらない）場合は「防御欠如」として扱い、指摘候補に追加する。部分防御は完全防御ではない。

## Step 4: 自己検証

出力前に以下を確認し、該当する指摘は削除または格下げする。

**「指摘候補」の定義**: Step 3 で問題として認識し、既存パターン照合でNO（一致なし）となった後に重要度判断まで進めたもの。照合でYESとなり即中止したものは候補に含めない。既存ファイルが存在しない（新規追加のみ）の場合は照合スキップ＝NOとして扱い、指摘候補として続行する。

### 基本確認
- [ ] Step 2 で取得した diff の実際のコードを参照しているか？
- [ ] PR description で既に説明・対処されていないか？
- [ ] 既存コメント・レビューと重複していないか？
- [ ] severity（[must]/[imo]）は変更の影響規模と一致しているか？

### 指摘の質の確認
- [ ] [must] で「ある保護が欠如している」と主張する場合、diff 外のコードでその保護が既に提供されていないことを確認したか？未確認なら [must] ではなく [ask] を使う
- [ ] [must] で「この式/コマンドの動作が誤っている」と主張する場合、実際に実行して確認したか？（例: `echo "${GITHUB_REF#refs/tags/*/*/}"` を Bash で実行してシェル展開結果を検証。確認できない場合は [ask] に格下げ）
- [ ] 同じパターンが既存の類似ファイルに存在しないか？（存在する = リポジトリ慣習 = 指摘対象外。GitHub Actions は sibling ワークフローを必ず確認。「今回は変更不要」「将来的な改善提案」「設計確認」という形でも出力しない）
- [ ] PR description の設計意図・目的と指摘が矛盾していないか？（矛盾している = 設計理解不足 = [must]/[imo] を下げるか削除する）

### AI特有の確認
- [ ] 追加された依存パッケージはすべて存在確認済みか？（未確認なら今すぐ確認する）
- [ ] 使用しているAPIが非推奨・CVE対象になっていないか確認したか？
- [ ] テストが実装と同一AIにより生成された可能性がある場合、テストが実装の盲点を共有していないか評価したか？
- [ ] 破壊シミュレーション（Step 3.5）の各シナリオで防御が確認できない箇所はすべて指摘候補に含めたか？

### 正確性の確認
- [ ] PR description が謳う機能・修正が diff に実際に存在するか確認したか？
- [ ] 境界値・null・空入力の処理が正しいことをパストレースで確認したか？

## Step 5: 出力フォーマット

```
## PR #NNN レビュー: <タイトル>

### 総評
（3-4文。PE 視点での全体印象・正確性評価・最重要懸念。
AIが書いたコードの場合はAI特有リスクの評価を含める）

### 指摘事項

**[must] `path/to/file:42`**: 問題の説明
> `diff から引用したコード`
→ 改善案: 具体的なコードまたは手順

**[imo] `path/to/file:87`**: 問題の説明
> `diff から引用したコード`
→ 改善案: ...

**[ask] `path/to/file:55`**: 設計意図の確認が必要な点
> `diff から引用したコード`
→ 確認事項: PR description から意図が読み取れないため確認したい点

### 良い点
- [good] `path/to/file:15`: 評価できる設計判断（コード引用は不要）

### 自己検証結果
全 N 件の指摘候補を確認。除外: N 件（根拠なし / PR description 説明済み / 既存コメント重複 / 既存パターン一致）
（除外件数 = Step 4 の検証で指摘候補から削除した件数。最終出力の指摘件数ではない）
```

問題がなければ `### 指摘事項` セクション内に「指摘事項なし。Approve 推奨。」と書く（見出しは省略しない）。
良い点がある場合は `### 良い点` セクションを含める（指摘事項なしでも出力してよい）。
`[good]` タグは `### 良い点` セクション専用。
`### 自己検証結果` の除外件数が 0 の場合は「除外: 0 件」と記載する。
