## Layout

| Path | Role |
|---|---|
| `.claude-plugin/plugin.json` | Name, version, description, author |
| `.claude-plugin/marketplace.json` | Source location used by `claude plugin install` |
| `skills/<skill-name>/SKILL.md` | Frontmatter and prompt body of one skill |
| `skills/<skill-name>/references/` | Optional large static documents the prompt pulls in |
| `agents/<agent-name>.md` | Portable subagent that APM deploys; only `name`, `description`, and `mode: subagent` frontmatter, and listed in `tests/validate-apm.sh` |
| `skills/orchestrate-epic/scripts/oe` | Shell helpers that read and write orchestrate-epic's state on GitHub and in host-local records, laid out in `oe-store.sh`; each `oe-<subcommand>.sh` header documents one subcommand |
| `skills/orchestrate-epic/scripts/oe-bot.sh` | The Bot identity an agent's worktree carries when its clone sets `skills.bot`, and the token the scripts that write to GitHub take from it |
| `skills/**/*.bats` | Script tests that `.github/workflows/lint-shell.yml` runs |
| `docs/design/orchestrate-epic.md` | The orchestrate-epic Design Doc that oe and the agents implement |
| `.github/rulesets/main.json` | The main-branch ruleset; the admin applies it with `.github/rulesets/apply.sh`, as its README describes |
| `.github/rulesets/tags.json` | The ruleset that limits `v*` tag creation to admins; applied by the same script |
| `.github/workflows/test-plugin-install.yml` | CI: `validate` then `test-install`, on push to `main` and every PR |
| `.github/workflows/secret-scan.yml` | CI: gitleaks on push to `main` and every PR |
| `.github/workflows/release.yml` | Creates a GitHub Release on a `v*` tag push, with notes generated by git-cliff, only when the guards in `.github/scripts/release.sh` hold |
| `.github/scripts/release.sh` | The release workflow's publish guards and Release notes, as `docs/design/release-flow.md` defines them; `tests/release.bats` runs it against a sandbox repository |
| `cliff.toml` | `git-cliff` config used by `make release` and by the Release notes |

`docs/design` holds only Design Docs that describe the current target, as `manage-design-documents` defines them; work the owner decided to build is an Issue.
Ideas, experiments, and open questions go to [Discussions](https://github.com/maro114510/skills/discussions) as [Development Flow](#development-flow) describes, never to Issues. The repository is public, so a post never carries work context.

## Versions and Releases

- Update both manifests together; updating only one breaks `claude plugin install`
- Bump versions with the Makefile release targets, never by hand
- `make release RUN=<commit>` infers the next SemVer from the Conventional Commits in the Release range via `git-cliff`, adds the Bump commit on a `release/v<version>` branch from the Run commit, and pushes that branch and the tag, never `main`
- Tags carry the `v` prefix, e.g. `v0.28.0`; manifest versions omit it, e.g. `0.28.0`
- Workflow actions are commit-pinned; update them with Dependabot only

| Bump | Commit type | Skill change |
|---|---|---|
| Major | `!` or `BREAKING CHANGE` | Breaking interface change or skill removal |
| Minor | `feat:` | New skill or meaningful new capability |
| Patch | `fix:` `perf:` `refactor:` `docs:` | Fix for ambiguity or a bug in a skill body |
| None | `ci:` `test:` `chore:` | - |

## Skill Format

```yaml
---
name: <skill-name>
description: >
  <Natural language description, also used for trigger-phrase matching>
disable-model-invocation: true
argument-hint: "[ready] [base <branch>]"
---
```

| Key | Rule |
|---|---|
| `description` | Matched against user requests; include phrasings users naturally say |
| `disable-model-invocation` | Optional; `true` only stops Claude from loading the skill automatically. It does not disable the agentic loop: the skill still runs through `/name` and calls its tools normally, as in `orchestrate-epic` |
| `argument-hint` | Shown on `/help` |

- The body is the full prompt; user arguments arrive as `$ARGUMENTS`
- Body language is English or the target repository's language
- Japanese stays only in `description` trigger phrases and user-facing output templates
- Convert an older Japanese body only when already editing it for another reason
- Do not declare `allowed-tools`: it only pre-approves tools in Claude Code and has no effect in OpenCode or Pi, so it cannot restrict a skill's tools on every supported harness

## Target Repository Config

Per-user or per-clone settings live in git config and are never committed.
Skills read them with `git config --get <key>`, so git decides between local and global.

| git config key | Values | Resolved by |
|---|---|---|
| `skills.lang` | `ja`, `en` | `skills/create-pr/scripts/lang.sh` only; its header holds the precedence, and skills call it instead of restating it |
| `skills.herdr` | `true`, `false`; unset means `false` | `skills/orchestrate-epic/scripts/oe-board.sh` only, and only inside Herdr; `true` opens the Epic's board pane |
| `skills.babysit.agent` | An agent command, such as `claude -p`; unset makes `drive.sh` exit 2 | `skills/babysit/scripts/drive.sh` only; split on whitespace, with the prompt appended as the last argument |
| `skills.notify` | A shell command, such as `herdr notification show "$1" --body "$2"`; unset or empty means no notification | `skills/orchestrate-epic/scripts/oe-wait.sh` only; run through `sh -c` with a one-line message as `$1` and a link as `$2` for each item that needs the person |
| `skills.bot` | The login of the GitHub App bot the agents act as, with or without the `[bot]` suffix; unset means none. A clone that sets it opts in: the worktree an agent gets carries the Bot's git user and credential helper, while the person's own checkout keeps the person's. Its remote and every push URL must be an HTTPS GitHub URL, and neither the clone nor the worktree an agent gets may have submodules, or a start refuses. The worktree also resets inherited `http.<url>.extraheader` values and ends the credential chain at the Bot helper, so a helper that declines fails the push instead of falling back to the person | `bot_def` in `oe-config.sh` and `babysit_bot` in `common.sh` read it for records; `bot_login`, `bot_identity_apply`, and `bot_require_ready` in `oe-bot.sh` give an agent's worktree its identity and refuse a start that could not hold it; `bot_env` makes the scripts that write to GitHub use a token for it |
| `skills.bot.helper` | A command that answers `token <owner>/<repo>` with one installation token for that repository, and git's credential helper protocol with `get`; read only from the global config, so a clone cannot name it | `bot_helper` in `skills/orchestrate-epic/scripts/oe-bot.sh` only |

## Development Flow

Every harness loads this file, but not every one follows an import from it, so these rules live here and nowhere else.

Route new work by two questions, in order:

1. Is what to do decided? If not, it goes to a Discussion.
2. Does the change move a boundary, such as a skill contract, user-visible behavior, a safety gate, a git config key, or a data format?

| Decided | Moves a boundary | Path |
|---|---|---|
| No | - | A Discussion |
| Yes | Yes | Intent in a Discussion, the owner's decision, a merged Design Doc, then an Epic driven by oe |
| Yes | No | An Issue |

- Create an Issue only after the owner wrote that the work will be done; a bug fix, or a fix such as a typo that changes no behavior, still gets an Issue, but needs no decision from the owner
- Keep at most 5 decided units open at once: an Epic counts as one, a standalone Issue counts as one, and a bug fix or a fix that changes no behavior does not count
    - A unit counts from when it starts, so a change that moves a boundary counts while its Design Doc is still open
    - While 5 are open, a newly decided unit waits in its Discussion without counting, and starts when one closes
- When the owner decides in a conversation and no Discussion holds the work, open one that states the intent and quotes the decision
- Close anything decided against with the observation that would reopen it
- Quote the question and the owner's answer behind each decision where it is recorded: the comment that closes a Discussion, and the body of a Design Doc pull request

### Discussions

| Category | Holds |
|---|---|
| Ideas | Experiments, evaluations, and research that nobody has decided to build |
| General | Open questions that need a decision |

- Search Discussions and Issues for the same topic first; comment on an existing Discussion instead of opening a duplicate, and link a related Issue, especially one that scopes the idea out
- State the evidence behind the post
- An improvement idea names what in the repository it would let us remove, or says none
- Write posts and Issues in English
- Keep general facts, such as error class and status, endpoint, counts, timing, and the skill involved
- Drop anything that identifies private work: names of private repositories, organizations, and app installations, their PR and Issue numbers, product and domain terms, code, and data
- When the owner decides to build an idea, start its path from the table above with a link to the Discussion, even if an older Issue for it was closed: a new Issue, or for a change that moves a boundary, a Design Doc pull request. Comment its URL on the Discussion, and close the Discussion when the Issue opens or the Design Doc merges
- Close a Discussion with the reason that fits, and state that reason in the closing comment
    - Resolved when the work the owner decided to build has started: its Issue opened or its Design Doc merged
    - Outdated when the owner decided against it, with the observation that would reopen it
    - Duplicate when another Discussion already holds it, linking that one

## Workflow

1. Create or edit `skills/<skill-name>/SKILL.md`
2. Commit with Conventional Commits
3. Run `claude plugin validate .`
4. Open a PR; CI validates and test-installs

claude plugin validate .

# Test the full installation flow
claude plugin marketplace add ./
