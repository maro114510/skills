# orchestrate-epic 設計

## 目的

Epic の子 Issue を依存順に検証済み PR へ変え、状態はすべて GitHub から導き、マージはエンジニアかリポジトリの自動化に任せる。

## 責務

各部品は 1 つの仕事だけを持ち、状態を持たない。

| 部品 | 仕事 | 使う部品 |
|---|---|---|
| orchestrate-epic | 次の行動を得てエージェントを起動し、変化を待つことを繰り返す | oe、pr-owner、pr-verify |
| pr-owner | Issue を 1 段だけ進めて push し、迷えば質問だけして何も push しない | implement、create-pr、oe question |
| implement | コードとテストを書いてコミットし、push はしない | commit |
| commit | 秘密情報を検査してコミットする | なし |
| create-pr | PR を作る | なし |
| pr-verify | 1 つの SHA を Issue の受け入れ基準で検証する | oe verdict |
| oe lock | 同じ Epic の 2 つ目のセッションを拒否する | なし |
| oe ready | GitHub を読み、Issue ごとの次の行動を出し、何も書かない | なし |
| oe claim | ブランチと着手記録を作る | なし |
| oe worktree | 共有チェックアウトの外に作業場所を用意し、終了時に消す | なし |
| oe attempt | 試行記録を書き、4 回目を拒否する | なし |
| oe brief | エージェントへの指示を作り、何も書かない | なし |
| oe question | 質問をマーカー付きで Issue に書く | なし |
| oe verdict | SHA に保留、成功、失敗のステータスを付け、指摘を PR に書く | なし |
| oe wait | oe ready の出力が変わるか時間切れまで待つ | oe ready |
| エンジニア | 答え、レビューし、マージし、ブランチを消してやり直させる | なし |

## 不変条件

| 不変条件 | 対応する Epic の安全条件 |
|---|---|
| AI はマージも自動マージ有効化もしない | マージ許可などマージ系の条件はすべて不要になる |
| 依存先がすべて完了で閉じてから着手する | 依存の完了 |
| 着手はブランチ作成で行い、既にあれば失敗する | 二重着手の防止 |
| 判定は検証した SHA のコミットステータスで、その SHA が PR の先頭のときだけ書く | 判定と SHA の結び付け |
| Verifier には Issue と SHA とベースだけを渡す | Verifier は作業者の報告を見ない |
| エージェントは 1 段ごとに新しく起動して終わる | 段ごとに新しいエージェント |
| Owner の試行は GitHub から数え、4 回目は拒否する | 再起動しても残る試行上限 |
| エージェントは自分の worktree だけで作業する | 共有チェックアウトに触れない |
| エンジニアの入力は信頼ユーザーのマーカーなしコメントだけで、ラベルは意味を持たない | 信頼できる入力だけを使う |
| GitHub の読み取りに失敗したら何も決めない | 読み取り失敗で判断しない |
| 起動が同意で、セッション終了ですべて止まる | 開始ゲートは不要になる |
| 本物の CI で判断する | ローカル再現の検査集合は不要になる |

秘密情報の検査は受容するリスクに対応する。

## 状態の導出

Issue は次の段階を進む。

```mermaid
flowchart TB
  subgraph Pre["着手前"]
    Blocked["依存待ち"] -->|"依存がすべて完了"| Ready["着手可能"]
  end
  subgraph Work["作業"]
    Owner["Owner 実行"] -->|"質問"| Ask["回答待ち"]
    Ask -->|"回答"| Owner
    Owner -->|"push"| CI["CI 待ち"]
    CI -->|"失敗か競合"| Owner
  end
  subgraph Check["検証"]
    Verify["Verifier 実行"] -->|"成功"| Merge["マージ待ち"]
  end
  Ready -->|"着手"| Owner
  CI -->|"成功"| Verify
  Verify -->|"失敗"| Owner
  Merge -->|"変更要求"| Owner
  Merge -->|"エンジニアがマージ"| Done["完了"]
  Owner -->|"試行 3 回"| Parked["停止"]
  CI -->|"10 分 check 無し"| Parked
  Verify -->|"判定無し 2 回"| Parked
```

oe ready は Issue ごとに、上から順に最初に当てはまる行の行動を出す。

| 順 | 段階 | GitHub の状態 | 次の行動 |
|---|---|---|---|
| 1 | 関門 | 既定ブランチの先頭に 10 分経っても check が無い | セッションを終える |
| 2 | 関門 | 既定ブランチの check が保留か失敗 | 何も始めない |
| 3 | 着手前 | Issue が閉じている | 完了 |
| 4 | 着手前 | 最新の着手後にマージ済み PR があるか、閉じた PR だけのブランチがある | エンジニアを待つ |
| 5 | 着手前 | ブランチが無く、依存が未完了 | 依存を待つ |
| 6 | 着手前 | ブランチが無く、依存がすべて完了 | 着手して Owner を起動する |
| 7 | 作業 | 未回答の質問がある | 回答を待つ |
| 8 | 作業 | 修理シグナルがある | Owner を起動し、試行 3 回なら停止する |
| 9 | 検証 | PR の check が保留 | CI を待つ |
| 10 | 検証 | PR の先頭に 10 分経っても check が無い | 停止する |
| 11 | 検証 | 判定が無い | Verifier を起動し、判定無しが 2 回なら停止する |
| 12 | 検証 | 成功判定がある | マージを待つ |

- 修理シグナル
  - PR が無い
  - 競合している
  - check が失敗している
  - 判定が失敗している
  - 最新の試行より新しい信頼ユーザーの回答、変更要求レビュー、レビュースレッドのコメント
- 数え方
  - 記録は最新の着手記録より後のものだけを数え、着手記録が無ければすべて数える
  - Verifier の回数は、起動前にその SHA へ付ける保留ステータスの数で数える
  - 自分の判定ステータスは check に含めない
  - 実行中のエージェントがいる Issue はセッション内で除く

## 具体例

正常系では、B は A に依存する。

```mermaid
sequenceDiagram
  autonumber
  actor H as エンジニア
  box rgb(235,242,255) AI
    participant O as orchestrate-epic
    participant E as oe
    participant W as pr-owner
    participant V as pr-verify
  end
  participant G as GitHub
  H->>O: 起動する
  rect rgba(0,120,255,0.08)
    Note over O,G: 着手
    O->>E: ready
    E->>G: 状態を読む
    E-->>O: A に着手
    O->>E: claim と attempt
    E->>G: ブランチと記録を作る
  end
  rect rgba(0,200,120,0.08)
    Note over O,G: 実装
    O->>+W: A を渡して起動する
    W->>G: push して PR を開く
    W-->>-O: 終了
    O->>E: wait
    G-->>E: CI が成功する
    E-->>O: A を検証
  end
  rect rgba(255,160,0,0.08)
    Note over O,G: 検証
    O->>E: brief
    O->>+V: A の SHA を渡して起動する
    V->>E: verdict で成功
    E->>G: SHA に成功を付ける
    V-->>-O: 終了
  end
  rect rgba(160,80,255,0.08)
    Note over H,G: マージ
    O->>E: wait
    H->>G: A をマージする
    G-->>E: A が閉じる
    E-->>O: B に着手
  end
```

| 場面 | 動き |
|---|---|
| エージェント消失 | GitHub に完了の印が無いので次の試行が同じブランチで始まり、セッションの再実行も同じ状態から再開する |
| 検証失敗 | 失敗判定と指摘コメントを受けて Owner が修理し、新しい先頭で CI と検証をやり直す |
| CI 失敗 | Owner が同じブランチで修理する |
| 上限到達 | 3 回で停止し、依存する Issue も待ち、エンジニアが手で仕上げるかブランチを消してやり直す |
| 既定ブランチの失敗 | 着手も Owner も Verifier も始めないので試行を消費せず、成功に戻れば再開する |

## 受容するリスク

- 共有トークンでは判定を偽造できる
- ベースが動いても再検証しない
- AI が変えたワークフローが秘密情報付きで動く
- oe は秘密情報を検査せず、各コミットは commit スキルが検査する
- マーカーを付け忘れた AI の書き込みはエンジニアの入力に見える
- セッションロックはホスト内だけなので、別ホストのセッションは拒否できない

## 決定事項

| 論点 | 決定 |
|---|---|
| 依存先が不要や重複で閉じた | 依存する Issue はエンジニアを待つ |
| 修理を起動するシグナル | 上の修理シグナルだけで、通常の PR コメントと bot のレビューは無視する |
| 回答後の再起動 | 試行上限 3 回に数える |
| Verifier が判定を出せない | 1 回だけ再試行し、2 回目で停止する |
| 待機 | oe wait は 1 回 25 分までで、4 時間変化が無ければ要約を出して終わる |
| 並列数 | Owner と Verifier の合計 3 で、引数で変えられる |
| worktree | エージェント終了時に消し、push していない作業は捨てる |
| 判定の指摘 | マーカー付きの PR コメントに書き、次の Owner が読む |
